# 生产级与企业级演进

## 1. 生产化目标

生产级平台要解决的不只是“能不能跑”，还要解决：

- 任务是否可复现。
- 不可信 Agent 是否被隔离。
- 结果是否可信、可追溯、可申诉。
- 多个用户和项目是否互相隔离。
- 运行失败后能否恢复。
- 高并发时是否有背压和资源控制。
- 成本是否可控。
- 审计日志是否完整。

## 2. 生产架构演进

```text
Web Console
    ↓
API Gateway / WAF
    ↓
Stateless API
    ├── PostgreSQL
    ├── Redis / Kafka
    ├── Object Storage
    └── Auth / Secret Manager
             ↓
       Run Scheduler
             ↓
    Kubernetes Runner
       ├── Agent Pod
       ├── Benchmark Pod
       ├── Scorer Pod
       └── Trace Collector
```

控制面服务必须无状态，运行任务必须异步化。用户点击“启动评测”只创建 Run 和 Job，不等待整个评测完成。

## 3. 高可用设计

### API 层

- 多副本部署。
- 负载均衡。
- 健康检查和优雅下线。
- 所有写接口使用幂等键。
- 长任务不占用 API 请求线程。

### 调度层

- Job 状态持久化。
- Worker 心跳。
- 租约和超时回收。
- 失败重试有次数上限。
- 任务级 checkpoint。
- 支持从最后一个已确认事件恢复。

### 数据层

- PostgreSQL 主从或云数据库高可用。
- 轨迹写入对象存储，数据库只存索引和摘要。
- Trace Event 使用 append-only 方式。
- 结果表和事件表分离。
- 定期备份和恢复演练。

### 运行层

- 每个 Trial 独立运行单元。
- Agent、Benchmark 和 Scorer 可分离部署。
- Runner 不信任 Agent 返回的数据。
- 限制 CPU、内存、磁盘、进程数、文件大小和运行时间。

## 4. 代码包执行安全

上传执行是最高风险功能之一，必须独立设计：

```text
上传
  → 病毒/恶意文件扫描
  → SBOM 和依赖解析
  → 隔离构建
  → 镜像签名
  → 漏洞扫描
  → 沙箱试运行
  → 审批
  → 生产 Runner 执行
```

建议安全策略：

- 非 root 用户。
- 只读根文件系统。
- 临时工作目录。
- 默认无外网。
- 只开放明确域名和端口。
- 禁止访问宿主机 Docker Socket。
- 禁止访问云平台元数据服务。
- 限制 Linux capabilities。
- 使用 gVisor 或 Kata Containers。
- 记录所有进程、网络、文件和系统调用异常。

## 5. Agent 与工具审计

平台需要分别审计 Agent 的声明和实际行为。

### 声明审计

- Agent 声明了哪些工具。
- 工具来源和版本。
- MCP Server 地址和版本。
- 模型、Prompt、Memory、Planner 的版本。
- Agent 代码包和镜像 Digest。
- 依赖许可证和漏洞信息。

### 行为审计

- 实际调用了哪些工具。
- 是否调用未声明工具。
- 是否传入越权参数。
- 是否绕过平台动作校验。
- 是否读取任务之外的文件或网络地址。
- 是否泄漏敏感信息。
- 是否违反用户确认或安全策略。
- 是否在失败后无限重试。

声明审计解决“理论上能做什么”，行为审计解决“实际上做了什么”。两者必须能在报告中对照查看。

## 6. 企业级权限模型

建议采用：

```text
Organization
  └── Project
      ├── Members
      ├── Agents
      ├── Datasets
      ├── Evaluation Templates
      ├── Runs
      └── Reports
```

角色至少包括：

- Owner：项目和成员管理。
- Admin：配置、Agent、数据集和运行管理。
- Evaluator：创建评测、执行 Run、查看 Trace。
- Developer：管理自己的 Agent 版本和查看结果。
- Viewer：只读查看报告。
- Auditor：查看审计记录和不可篡改证据。

敏感数据应增加字段级权限，尤其是：

- Prompt 原文。
- 用户输入。
- 工具参数。
- 代码和文件。
- API 返回数据。
- 评测集答案。

## 7. 凭证管理

- 不把模型 API Key 存在 Agent 配置明文中。
- 使用 Vault、云 Secret Manager 或 Kubernetes Secret。
- 每个 Run 使用短期凭证。
- 外部 Agent 使用独立 client credential。
- 工具凭证按 Project、Agent、Session 隔离。
- Trace 中默认脱敏。
- 所有凭证访问写入审计日志。

## 8. 结果可信性

生产报告必须展示结果来源，而不是只展示一个百分比：

```text
结果
 ├── 数据集版本
 ├── 任务样本和采样规则
 ├── Agent 版本和镜像 Digest
 ├── 模型版本和参数
 ├── Prompt / Tool Schema 版本
 ├── 环境镜像
 ├── Scorer 版本
 ├── 原始 Trace
 ├── 原始评分
 └── 平台聚合规则
```

Benchmark Adapter 必须支持 parity 验证，保证平台适配后的结果和原始 Benchmark 的结果具有可比性。

如果数据集、评分器、模型或 Agent 在运行期间发生变化，该 Run 必须标记为不可复现或配置漂移。

## 9. 成本和资源治理

每个 Run 和 Trial 都应支持：

- 最大步骤数。
- 最大运行时间。
- 最大模型调用次数。
- 最大 Token 数。
- 最大成本。
- 最大并发。
- 失败重试次数。
- 单 Agent 日配额。

成本统计至少包含：

- 模型输入 Token。
- 模型输出 Token。
- 推理 Token（若供应商提供）。
- 工具调用次数。
- 沙箱运行时间。
- GPU/CPU 资源时间。
- 外部服务费用。

## 10. 可观测性

建议使用 OpenTelemetry 作为底层 Trace 标准，但平台需要额外补充评测字段：

```text
trace_id
run_id
trial_id
session_id
agent_id
agent_version
benchmark_id
dataset_version
dimension_id
scorer_version
```

指标分三类：

### 运行指标

- 排队时间。
- 启动耗时。
- 任务耗时。
- Worker 利用率。
- 容器启动失败率。
- 任务超时率。

### Agent 指标

- 任务成功率。
- 工具选择准确率。
- 参数错误率。
- 无效调用率。
- 平均步骤数。
- 失败恢复率。
- 每任务成本。

### 平台指标

- 调度延迟。
- 队列积压。
- API P95/P99。
- Trace 写入延迟。
- 评分器失败率。
- 报告生成耗时。

## 11. 灾备和数据保留

建议按数据类型设置保留策略：

- Run 元数据：长期保留。
- 分数和报告：长期保留。
- 原始 Trace：按项目策略保留 30～180 天。
- 大文件和截图：按成本策略分层存储。
- 敏感输入：默认短期保留或只保留摘要。
- 审计日志：按合规要求长期保存、禁止普通管理员删除。

至少需要：

- PostgreSQL 自动备份。
- 对象存储版本控制。
- 跨可用区副本。
- 定期恢复演练。
- 关键 Run 的导出包。

## 12. 企业级实施路线

### 阶段一：本地 Demo

- React + FastAPI。
- SQLite。
- 内置 Mock Agent 和 Mock Benchmark。
- 单进程 Runner。
- JSONL Trace。

### 阶段二：单机生产版

- PostgreSQL。
- Redis 队列。
- Docker Worker。
- MinIO 对象存储。
- OpenTelemetry。
- 基础登录和项目隔离。

### 阶段三：企业内部版

- Kubernetes Job。
- RBAC。
- Vault/Secret Manager。
- Agent 代码包构建和扫描。
- 审批流。
- 运行预算。
- 审计日志和报告导出。

### 阶段四：高可用平台

- API 多副本。
- Runner 多节点。
- 队列分区和优先级。
- 失败恢复和 checkpoint。
- 远程沙箱。
- 多模型、多供应商路由。
- 数据库和对象存储灾备。

### 阶段五：企业级评测中台

- 多租户。
- SSO/OIDC/LDAP。
- 组织级数据隔离。
- 细粒度权限和审批。
- 评测模板市场。
- 生产 Trace 自动生成回归集。
- 线上漂移监控。
- CI/CD 评测门禁。
- 结果签名、不可篡改存证和合规审计。

## 13. 最终建议

平台的主线不应是“做一个漂亮的评测 Dashboard”，而应是：

```text
稳定协议
  + 可复现任务
  + 可隔离执行
  + 可追踪轨迹
  + 可解释评分
  + 可审计配置
  + 可治理 Agent
```

第一版先实现一个完整但小的闭环，再扩展 Benchmark 数量。只有当 Task、Action、Observation、Trace、Score 和版本快照稳定之后，接入更多 Benchmark 才不会变成不断堆特殊逻辑。
